# 整合測試品質評估器（ITQA）

使用此框架評估整合測試套件、診斷失敗，以及在不隱藏產品缺陷的前提下提升測試可靠性。方法不綁定程式語言、測試框架、資料庫、服務類型或測試執行器。

## 範圍與操作規則

- 先檢視 repository 的測試指令、fixture、環境契約與結果格式，再選擇指令或模式。
- 優先使用專案原生測試執行器與機器可讀的結果輸出，不要假設執行器、檔案副檔名、資料庫、託管模型或 assertion 函式庫。
- 將測試失敗視為證據。在修改程式碼前保留原始錯誤、執行上下文與可重現性資訊。
- 優先修正測試層或測試環境。只有在失敗證明產品缺陷，或需求明確包含該變更時，才修改產品程式碼。
- 不得用 retry、skip、過寬的例外處理、放寬 assertion 或替代資料路徑掩蓋失敗。每個例外都必須明確且有理由。
- 技術特定的實作細節應放在專案自己的測試文件；本技能的參考資料只用於推理模式，不作為特定框架設定的複製貼上範本。

## 三階段評估

### 第一階段：建立基準線

1. 找出 repository 文件所定義的測試指令，以及支援的本機或 CI 環境。
2. 執行完整整合測試範圍一次，並保存原始輸出及可用的結構化結果。
3. 記錄總數、通過、失敗、略過、待處理、阻塞、耗時與環境資訊。略過、待處理與阻塞測試必須分開回報，不得靜默計為通過。
4. 保存基準版本、設定檔、相依套件版本、資料來源與平行執行設定。
5. 套用專案品質門檻。若沒有既定門檻，使用 95% 作為暫定閘門，並在報告中標記這項決策。

### 第二階段：根據證據診斷

1. 單獨重跑每個失敗，再在可能涉及順序或共享狀態時與完整套件結果比較。
2. 保留第一份有用的 stack trace、log、請求或訊息資料、fixture 狀態與時序資訊。
3. 使用[決策框架](references/decision-framework.md)分類失敗：環境、設定或 fixture、資料或外部相依、並行或時序、產品缺陷，或未知。
4. 選擇最小的測試層修正，恢復預期的整合邊界，同時不削弱 assertion。
5. 在修改另一個範圍前，先用聚焦執行驗證修正。
6. 對需要修改產品、Schema 或契約，以及測試層無法忠實提供的環境限制，附上證據與明確後續行動再升級。

### 第三階段：驗證與報告

1. 執行聚焦測試、完整套件，以及足以驗證可重現性的重複執行。診斷 flaky 或共享狀態風險時，至少進行三次獨立執行。
2. 檢查隔離、清理、順序獨立性、序列執行行為與設定的平行模式。
3. 執行[品質檢查清單](references/quality-checklist.md)，包含已知限制與略過測試審查。
4. 依下方結構產生報告，區分已觀察事實、假設、修正與剩餘風險。

## 失敗分類快速參考

| 分類 | 常見訊號 | 優先處理方式 | 產品程式碼風險 |
|---|---|---|---|
| **環境** | 執行環境能力、設定、網路、檔案系統、時鐘或服務缺失 | 明確化測試環境；加入狹窄的 adapter 或前置條件防護 | 生產行為未變更時為低 |
| **設定／Fixture** | 測試間狀態洩漏、清理不完整、安排無效或依賴順序 | 隔離設定與清理；使用確定性的 fixture builder | 低 |
| **資料／相依** | Seed 資料、憑證、Schema、服務或契約缺失或不相容 | 使用確定性 fixture 或依能力探索；驗證相依契約 | 低至中 |
| **並行／時序** | Race、timeout、最終一致性或只在平行執行時失敗 | 依可觀察條件同步；隔離共享狀態；移除時序假設 | 中 |
| **產品缺陷** | 系統違反已定義需求、不變量、Schema 或 API 契約 | 保留失敗 assertion，修正或升級產品缺陷；只使用有文件的暫時方案 | 中至高 |
| **未知** | 證據不足或互相矛盾 | 先取得一個能區分假設的觀察，再修改 | 未知 |

## 品質閘門

每次評估都應回答：

- 實測通過率是否達到設定門檻，且略過、待處理與阻塞測試均已揭露？
- 在支援的環境與平行設定下，結果是否可以重現？
- 每個失敗是否根據證據歸屬到某一層，而不是只依例外名稱猜測？
- 測試變更是否保留行為與整合 assertion 的強度？
- 環境前置條件、資料所有權、清理、機密處理與外部相依是否明確？
- 已知限制是否以影響、負責人與下一步追蹤，而不是用 suppression 隱藏？
- 產品變更是否與測試基礎設施變更分開，並以正確風險層級審查？

完整閘門與報告要求請使用[品質檢查清單](references/quality-checklist.md)。

## 可重用模式

從[測試模式](references/test-patterns.md)選擇最小適用模式：

1. **環境 adapter**：保留生產環境解析方式，同時提供有文件的測試環境 adapter。
2. **確定性 Fixture 或能力探索**：從受控 fixture 取得有效資料，或在執行前驗證必要能力；不得猜測身份或記錄。
3. **上下文與相依 harness**：建立測試真正需要的請求、身份、時鐘、佇列、服務與儲存邊界，並在結束時清理。
4. **保留證據的暫時方案**：只有在仍可觀察預期行為，且已記錄失去的覆蓋範圍時，才暫時繞過損壞的非目標層。
5. **能力防護**：只有在前置條件確實不可用時才標記阻塞，並提供清楚原因與獨立後續工作。
6. **Flaky 隔離**：先在受控順序與平行設定下重現，再考慮 retry；retry 只能涵蓋已知暫時性邊界，且必須在結果中可見。

## 升級標準

下列情況應升級給負責工程團隊：

- 必須修改產品行為、Schema 或公開契約；
- 暫時方案會削弱被驗證的行為，或超過約定期限仍會存在；
- 測試邊界無法提供或忠實模擬必要的環境能力；
- 隔離與蒐證後仍有非決定性失敗；
- 共享狀態、test double 或 workaround 影響套件的重要部分；或
- 無法透過聚焦驗證界定觀察到的風險。

若只是本機測試設定不完整，而確定性、具文件的測試層修正即可解決且不削弱 assertion，則不必僅因此升級。

## 評估報告格式

所有評估應產出以下結構：

```markdown
## 整合測試評估：[專案或套件]

**狀態**：READY | ESCALATION REQUIRED | BLOCKED
**環境**：[執行器、設定、相依狀態與平行模式]

| 指標 | 數值 |
|---|---|
| 總數 | X |
| 通過 | X (Y%) |
| 失敗 | X |
| 略過／待處理／阻塞 | X |
| 耗時 | [數值] |
| 重複執行 | [結果] |

### 根本原因細分
- **環境**：[數量、證據、測試層行動]
- **設定／Fixture**：[數量、證據、測試層行動]
- **資料／相依**：[數量、證據、處置]
- **並行／時序**：[數量、證據、處置]
- **產品缺陷**：[數量、證據、負責人與後續]
- **未知**：[數量、下一個區分性檢查]

### 品質閘門
- [ ] 達到門檻且已揭露排除項目
- [ ] 失敗已根據證據分類
- [ ] 已檢查可重現性與隔離
- [ ] 已審查產品影響
- [ ] 已記錄有負責人與後續行動的已知限制

### 詳細發現
[每個測試或失敗的證據、修正、驗證結果與剩餘風險]
```

## 新套件工作流程

1. **探索**：閱讀 repository 的測試與 CI 設定，確認整合邊界及必要服務。
2. **建立基準線**：執行原生套件一次並保存結構化結果。
3. **診斷**：分類失敗，為每個假設選擇一個聚焦檢查。
4. **修正**：優先修改測試層，保留 assertion，並記錄任何限制。
5. **驗證**：執行聚焦測試、完整套件，以及符合風險的重複執行。
6. **報告**：完成評估格式，並以證據交接產品缺陷或環境工作。

隨附的 PowerShell 輔助腳本可以執行專案提供的測試指令並產生初始報告。它不假設特定執行器，也不會解析所有結果格式；若測試指令使用自訂摘要，請檢查並補完產出的報告。
